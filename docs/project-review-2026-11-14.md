# 工业品导购 Agent 项目评审与改进路线

> 评审日期：2026-11-14  
> 评审方式：静态阅读 README、测试清单及当前前后端源码；本次未运行后端、前端或业务测试。  
> 文档用途：记录当前不足、代码证据、影响、改进思路和实施优先级，供阿渔渔（本地 Kimi Code）、阿渔（DSH）及主人后续协作时共同参考。  
> 注意：本文是评审与建议，不代表其中改造已经实施，也不代替具体任务的执行计划。

---

## 1. 总体判断

项目已经具备较完整的演示链路：自然语言采购、缺参追问、多轮补充、多需求拆分、混合检索、Excel 与图片上传、会话恢复、评价和三栏结果展示均已落地。

当前主要矛盾不是“功能数量不够”，而是以下四项基础能力没有跟上功能扩张：

1. **业务正确性**：部分链路可能把信息不全、规格不符或库存未确认的商品标成“可下单”。
2. **状态一致性**：规则解析、LLM 理解、历史拼接和检索改写多套逻辑并存，没有唯一的结构化需求状态。
3. **结果可验证性**：检索排序依赖人工观察，现有测试以打印和人工清单为主，缺少自动断言与相关性指标。
4. **问题可定位性**：反馈只有好评/差评，没有足够的运行轨迹区分理解、召回、排序和生成错误。

因此建议把后续重点从“继续加外围功能”调整为：

> 先保证不给错答案，再让系统可评估、可迭代，最后扩大商品规模和补充产品能力。

### 1.1 按不同目标看待当前完成度

| 目标 | 当前判断 |
| --- | --- |
| 本地功能演示 | 完成度较高，主要场景和界面都已具备 |
| 简历 / 面试项目 | 素材丰富，但需要能用测试、指标和追踪信息支撑设计取舍 |
| 真实采购工具 | 仍有明显距离，首先要消除错误的行动信号，再补真实商品和交易数据 |

## 3. P0：优先消除错误的业务结论

### 3.1 Excel 和图片行缺少关键参数，也可能被标成“可下单”

**代码证据**

对话多需求分支 `_multi_reply()` 会检查 `demand["missing"]`，缺参时给参考候选并标注“参数不全”：

- `backend/app/main.py:241-258`

上传链路 `_match_rows()` 则只要识别出品类就执行检索，随后直接调用 `_row_note()`：

- `backend/app/main.py:563-581`

`_row_note()` 只判断是否有结果、软属性是否冲突、数量是否低于 MOQ，没有检查 `demand["missing"]`：

- `backend/app/main.py:536-547`

**具体影响**

例如 Excel 行是「M8 螺丝 1000 个」，缺少长度。只要检索有结果、首推商品没有软属性冲突且 MOQ 满足，就可能被标成“可下单”。这比“首位排序不理想”更严重，因为它向采购员发出了错误的行动信号。

**改进思路**

统一对话多行、Excel 和图片的行评估逻辑，不再分别维护判断规则。建议形成一个统一的 `evaluate_row(demand, items)`，按固定顺序判断：

1. 库外品类。
2. 缺品类。
3. 缺关键参数。
4. 无精确匹配。
5. 硬约束不符，仅有替代品。
6. 软属性冲突。
7. MOQ、库存、报价等交易条件不满足。
8. 可下单。

缺关键参数时可以返回参考候选，但状态只能是“缺参数，暂不可下单”。

**完成标准**

- 同一行需求无论从对话、多需求、Excel 还是图片进入，状态判断一致。
- 缺 M 号、长度、内径等关键参数时，任何链路都不能返回“可下单”。
- 自动化测试覆盖上述四种入口的等价用例。

### 3.2 “可下单”未校验库存，语义超过实际判断范围

**代码证据**

商品表存在 `stock` 字段：

- `backend/app/models.py:22`

但 `_row_note()` 没有使用库存，价格是否实时、报价是否有效也没有对应状态：

- `backend/app/main.py:536-547`

**具体影响**

当前“可下单”实际只表示：有候选、未检测到部分属性冲突、数量达到 MOQ。它不代表库存充足，也不代表价格和交期仍然有效。

**改进思路**

短期内不必立即接真实 ERP，但应让状态和文案与证据一致：

- `可下单`：参数、MOQ、库存等演示数据中的必要条件都满足。
- `参数匹配`：选型条件匹配，但交易条件仍需确认。
- `需询价`：价格为空或不是有效报价。
- `库存不足`：需求数量超过可用库存。
- `交期待确认`：没有可靠交期数据。

如果项目仍只用于演示，可以保留静态库存，但必须在判断逻辑和界面文案中明确口径。

**完成标准**

- “可下单”的判断条件有代码和测试明确支撑。
- 库存为空或不足时不会误标。
- 界面和 README 对各状态含义采用同一套定义。

### 3.3 硬过滤为空后静默回退，可能把错误规格作为普通推荐返回

**代码证据**

`hybrid_search()` 对参数硬过滤后，如果没有剩余候选，会继续使用未过滤的融合排名：

- `backend/app/rag/retriever.py:119-124`

**具体影响**

用户要 `M8×30` 时，如果库里没有完全匹配的 SKU，系统可能继续返回 `M10×30` 或 `M8×50`。当前返回结构没有明确区分“精确匹配”和“硬约束不符的替代品”。

工业选型中，规格不符不是普通的相关性降低，而可能意味着商品无法安装或使用。

**改进思路**

将检索结果拆成：

- `exact_items`：满足全部硬约束。
- `alternatives`：不满足部分约束的候选，并附带 `mismatches`，逐项说明差异。

没有精确结果时使用明确的 `no_exact_match` 状态。替代品可以展示，但必须标注“规格不符，仅供替代选型”，不能进入普通“可下单”判断。

**完成标准**

- 无精确匹配时不静默退回普通推荐。
- 每个替代候选都能说明哪个参数不匹配。
- 检索测试覆盖“有精确结果”“只有替代品”“完全无结果”三类情况。

### 3.4 LLM 改写文本仍会影响硬过滤，与设计说明不一致

**代码证据**

`_rewrite_query()` 的注释说明“只影响召回，硬过滤仍用规则解析出的参数”：

- `backend/app/main.py:55-69`

但实际调用把 LLM 改写后的 `q_for_search` 整体传给检索：

- `backend/app/main.py:369-370`

`hybrid_search()` 又从传入字符串重新提取硬过滤参数：

- `backend/app/rag/retriever.py:120`

**具体影响**

只要改写文本漏掉、改变或新增数字，硬过滤条件就可能变化。这与“模型负责理解，代码负责校验硬约束”的设计目标冲突，也使幻觉有机会进入最关键的规格判断。

**改进思路**

检索接口明确分离两类输入：

```python
hybrid_search(
    semantic_query=rewritten_query,
    constraints=validated_params,
    ...
)
```

- `semantic_query`：允许使用 LLM 改写，只用于向量与 BM25 召回。
- `constraints`：只能来自代码校验后的结构化参数，不再从改写文本二次提取。

**完成标准**

- 改写器输出任意文本都不会改变硬约束。
- 检索函数不再负责理解用户需求，只执行召回、约束过滤和排序。
- 有测试证明“语义改写异常时，规格过滤仍保持原值”。

## 4. P1：统一理解、排序和推荐的可信度

### 4.1 多轮理解没有唯一的结构化需求状态

**代码证据**

当前一轮对话可能同时经过：

1. `understand.py` 调 LLM 输出结构化行。
2. 将结构化行重新拼成 `query` 字符串。
3. 再由 `parse_demand()` 用规则解析。
4. 必要时继续使用 `merge_with_history()`、`history_demand()`、`merge_demand()`。

相关位置：

- `backend/app/main.py:282-339`
- `backend/app/demand.py:208-314`
- `backend/app/understand.py:47-97`

**具体影响**

现有方式能处理“补充参数”和“后值覆盖前值”，但缺少表达以下语义的字段和操作：

- 「不要 304 的」：删除材质或增加否定条件。
- 「长度不限」：清除长度约束。
- 「刚才的不要了，换成轴承」：切换品类并清理旧品类专属参数。
- 「不要这个品牌」：增加排除条件，而不是写成普通文本。
- 多项需求中只修改其中一项。

结构化理解结果最终又被压回字符串，模型即使理解了修改或否定，也没有可靠的状态结构承接。

**改进思路**

建立唯一的会话需求状态，例如：

```json
{
  "category": "紧固件",
  "constraints": {
    "spec_m": "M8",
    "length": "30mm",
    "material": "304不锈钢"
  },
  "excluded": {
    "brand": ["某品牌"]
  },
  "quantity": 1000
}
```

理解层输出对状态的操作，而不是重新拼一句自然语言：

- `set`：设置或覆盖字段。
- `remove`：删除已有条件。
- `add_exclude`：增加否定条件。
- `switch_category`：切换品类并清理不兼容字段。

代码负责校验操作、合并状态和计算缺参。模型不可用时仍保留规则链路作为降级，但正常路径不应再由多套逻辑争夺“当前需求是什么”。

**完成标准**

- 补充、覆盖、删除、否定和换品类都有明确状态变化。
- 同一多轮用例重复执行结果稳定。
- 历史回放、LLM 理解和规则降级不会生成互相冲突的需求。

### 4.2 电气参数已解析，但没有进入统一硬约束

**代码证据**

`extract_params()` 会提取电压、电流到 `params["electrical"]`：

- `backend/app/demand.py:165-167`

检索 `_match()` 只检查内径、长度和 M 号：

- `backend/app/rag/retriever.py:79-86`

**具体影响**

「断路器 16A」目前主要依赖文本召回和排序，并不是代码保证的精确电流匹配。商品增多后，16A、32A 等相似 SKU 更容易混淆。

**改进思路**

将硬约束从三个特殊判断扩展为统一的参数定义：

- 每个参数有标准字段、单位归一化、比较方式和适用品类。
- 电压、电流、外径、螺纹规格、长度等采用同一套约束执行机制。
- 不再为每个新参数单独增加一个零散正则和排序补丁。

**完成标准**

- 电气参数不符的商品不会进入精确结果。
- 参数定义能说明适用品类和单位，不出现跨品类误用。

### 4.3 多次重排使最终优先级难以解释

**代码证据**

检索在 RRF 后依次执行头型重排、型号重排和软属性重排：

- `backend/app/rag/retriever.py:126-153`

最后一次软属性排序只使用软属性命中数和 RRF 分数，可能重新打散此前型号或头型形成的优先级。

**具体影响**

最终首位为什么是某个商品，很难用统一规则解释。新增一个排序因素也可能意外改变已有场景。

**改进思路**

把排序统一为单层决策：

1. 硬约束过滤。
2. 精确型号、精确规格等强匹配优先级。
3. 软属性加权分。
4. RRF 分作为相关性和并列时的补充。
5. 输出每个商品的匹配原因和扣分原因。

不要在不同阶段反复覆盖前一阶段的排序语义。

**完成标准**

- 型号、头型、软属性同时出现时，优先级有明确规则。
- 每个首位结果可以生成可读的排序解释。
- 关键场景有固定回归用例。

### 4.4 推荐正文自由生成，事实可能与候选不一致

**代码证据**

候选商品以文本形式交给 LLM，模型直接生成推荐正文：

- `backend/app/main.py:382-392`
- `backend/app/prompts.py:45-52`

README 已记录候选编号和列表顺序偶尔不一致的已知限制。

**具体影响**

即使前端卡片正确，正文仍可能说错编号、价格、产地或匹配原因。用户会同时阅读正文和卡片，两者冲突会削弱可信度。

**改进思路**

模型只生成解释，不生成事实字段。建议输出：

```json
{
  "recommendations": [
    {
      "product_id": 12,
      "matched": ["M8", "30mm", "304不锈钢"],
      "warnings": ["MOQ 1000"],
      "reason": "规格和材质完全匹配"
    }
  ]
}
```

后端校验 `product_id` 必须属于本次候选。名称、价格、规格、MOQ、产地等事实全部由代码根据数据库记录渲染。模型输出不合法时使用模板。

**完成标准**

- 模型无法引入候选之外的商品 ID。
- 价格、规格等事实不由模型自由填写。
- 正文、卡片和表格使用同一份结果数据。

## 5. P1：建立可评估、可定位、可回归的迭代能力

### 5.1 检索对比仍依赖人工观察，没有标准答案和指标

**当前状态**

项目已有向量、BM25 和 RRF 的对比脚本，也有人工测试清单，但尚未形成固定黄金集。45 条种子商品上的少量示例不足以证明某种检索方案在扩库后仍然有效。

**改进思路**

先建立 30～50 条高质量评估用例，不必等待万级 SKU：

- 每条包含用户 query、可选历史、相关商品 ID、必须满足的硬约束和期望首位。
- 覆盖完整规格、缺参、型号、软属性、无精确匹配、库外和多轮补充。
- 指标使用 `Recall@3`、`MRR`、硬约束违反率和无精确匹配识别率。
- 把“正确商品是否进入候选”和“进入后排第几”分开统计。

**完成标准**

- 每次修改 embedding、RRF、同义词或排序规则，都能运行同一评估集比较。
- 结果不只展示商品名，还给出指标变化和失败用例。

---

### 5.2 评价数据无法定位失败阶段

**代码证据**

`feedback` 只保存消息 ID、会话 ID、评价和时间：

- `backend/app/sessions.py:28-33`
- `backend/app/sessions.py:133-150`

**具体影响**

拿到差评后，缺少本轮理解输出、最终需求、改写 query、候选排名、过滤回退和模型错误信息，无法稳定地区分是理解错、召回错、排序错还是正文生成错。

**改进思路**

增加轻量 `trace` 记录，并与 `message_id` 关联。至少保存：

- 请求 ID、会话 ID、消息 ID。
- 理解层原始输出和校验结果。
- 最终结构化需求与缺参。
- 实际检索 query、硬约束、候选 ID、向量/BM25/RRF 排名。
- 是否回退、是否使用模板、模型错误类型。
- 各阶段耗时和模型名称。

敏感信息不进入 trace，日志中不记录 API Key 等内容。

**完成标准**

- 任意一条差评都能回看本轮关键阶段。
- 能按失败阶段统计问题，而不只统计好评率。

---

### 5.3 现有测试以打印为主，无法自动防回归

**代码证据**

- `backend/test_demand.py:17-22`：打印解析结果，没有断言。
- `backend/test_search.py:21-24`：打印检索结果，没有断言。
- `docs/test-checklist.md`：是完整的人工回归清单，但需要人工逐项执行和判断。

**具体影响**

修改主链路后，旧功能是否被破坏主要依赖人工记得执行哪些脚本并观察输出。随着协作者增多，这种方式更容易出现重复测试和判断口径不一致。

**改进思路**

优先把已经人工验证的用例转成自动化，而不是先追求覆盖率：

1. 需求解析：断言品类、参数、数量、材质和缺参。
2. 多轮状态：补充、覆盖、否定、删除和换品类。
3. 检索：硬约束、型号优先、无精确匹配和替代品。
4. 行评估：缺参数、属性不符、MOQ 和库存。
5. API：使用 FastAPI TestClient 覆盖主分支。
6. LLM：通过注入固定响应测试，保证离线可运行。

**完成标准**

- 一个统一命令可以运行核心回归。
- 测试失败有明确断言，而不是只打印一组待人工判断的商品名。
- 人工清单保留用于界面和真实模型验收，不再承担全部代码回归职责。

## 6. P2：工程鲁棒性和产品边界

### 6.1 上传接口存在同步阻塞和资源限制缺失

**代码证据**

- `/api/chat/upload` 使用 `async def`，内部执行同步图片识别、向量编码、检索和模型请求：`backend/app/main.py:584-623`。
- 文件一次性读入内存：`backend/app/main.py:589`。
- 未见统一的文件大小、图片尺寸和 Excel 行数限制。

**具体影响**

大文件或慢模型请求会占用服务资源；异步路由中的同步工作还可能阻塞事件循环。本地演示影响有限，多用户或批量上传时问题会放大。

**改进思路**

- 明确采用同步路由交给线程池，或把阻塞工作移入工作线程。
- 限制文件字节数、Excel 行数、图片尺寸和支持的真实内容类型。
- 错误响应使用稳定、用户可理解的文案，内部异常写入日志。

---

### 6.2 前端聊天请求没有检查 HTTP 状态

**代码证据**

`send()` 直接解析响应 JSON，没有像上传逻辑一样检查 `res.ok`：

- `frontend/src/App.tsx:454-485`

**具体影响**

后端返回 400/500 时，前端仍把响应当作正常 `ChatResponse`，可能出现空气泡或 `undefined` 内容。

**改进思路**

- 与上传逻辑一致，先检查 `res.ok`，再读取业务字段。
- 对网络错误、HTTP 错误和业务空结果分别展示。
- 请求期间切换会话时使用请求序号或取消机制，避免旧请求结果追加到新会话界面。

---

### 6.3 单需求商品卡没有直接展示规格

**代码证据**

商品卡的属性行包含品牌、品类、材质和型号，但没有 `spec`：

- `frontend/src/App.tsx:120-133`

**具体影响**

规格是工业选型最关键的字段之一。多需求表格有规格，单需求卡片反而不直观，采购员需要依赖正文或描述核对。

**改进思路**

在卡片主属性区直接展示 `spec`，型号作为独立字段保留；属性冲突和精确匹配状态也应在卡片上有明确标签。

---

### 6.4 会话和接口目前只适用于受信的本地演示环境

**代码证据**

- CORS 允许全部来源：`backend/app/main.py:125-130`。
- 会话没有账号或用户隔离。
- 会话、评价等接口没有鉴权。

**改进思路**

本地演示可以暂不做账号体系，但部署前应补：

- CORS 白名单。
- 用户身份和会话归属。
- 删除、评价和上传接口的权限校验。
- 上传限流、日志脱敏和配置管理。

---

### 6.5 领域模型距离真实采购仍有缺口

当前八维商品模型适合演示，但真实选型还需要逐步补充：

- 公差、强度等级、牙距、防护等级、安装方式等品类专属参数。
- 标准件标准号与厂家型号的关系。
- 单位换算和包装量，例如一盒包含多少个。
- 阶梯价、含税状态、运费和报价有效期。
- 供应商、授权资质、质保和货源。
- 替代料的完全替代、条件替代和不可替代关系。

不建议继续把所有信息塞进通用 `spec` 字符串。扩品类前应先定义通用字段与品类扩展字段的边界。

## 7. 建议的统一目标结构

后续改造可以围绕下面这条主链路收敛：

```text
用户输入 / 文件行
        ↓
结构化理解与校验
        ↓
唯一需求状态（参数、否定、数量、历史修改）
        ↓
缺参判断与追问
        ↓
语义召回（query） + 硬约束（validated constraints）
        ↓
精确结果 / 替代结果 / 无结果
        ↓
统一业务评估（缺参、属性、MOQ、库存、报价）
        ↓
事实由代码渲染，LLM 只补充推荐理由
        ↓
消息、结果、trace、反馈关联保存
```

这个结构的重点不是增加模块数量，而是明确各层职责：

- 模型负责理解自然语言和生成解释。
- 代码负责状态、参数、业务判断和事实。
- 检索负责召回与排序，不重新解释需求。
- 所有入口共用同一套业务评估。
- 每次结果都能被测试、追踪和复盘。

## 8. 修订后的实施路线图

### P0：业务正确性与核心回归

| 工作项 | 目标 | 完成标准 |
| --- | --- | --- |
| 统一行评估 | 消除多需求、Excel、图片判断差异 | 缺关键参数任何入口都不能“可下单” |

| 修正“可下单”口径 | 让库存、报价和文案一致 | 状态定义有代码与测试支撑 |
| 前端基础修正 | 规格可见、HTTP 错误可见、旧请求不串会话 | 关键界面行为人工验收通过 |
| 核心自动化测试 | 把已有基线转为断言 | 统一命令可运行，关键用例全绿 |

### P1：状态、评估和可观测性

| 工作项 | 目标 | 完成标准 |
| --- | --- | --- |

| 上传限制与部署安全 | 支持受控的多用户环境 | 鉴权、隔离、限流、文件限制和日志脱敏到位 |

## 9. 协作实施约定

本文列出的是整体方向，不意味着一次性全部改造。后续每个阶段仍应：

1. 明确本次只解决哪一个问题。
2. 先读当前实现、调用方和边界条件。
3. 在对话中列出改动文件、步骤、风险和验证方式。
4. 主人确认后再修改代码。
5. 完成后更新 `.agent-handoff/current.md` 和当日交接日志。
6. 已验证、只读代码确认、尚未验证的建议必须分开表述。

## 11. 一句话结论

当前项目最值得投入的，不是继续增加演示功能，而是把“听懂需求 → 找对商品 → 如实判断 → 自动回归 → 差评可定位”这条主链路做扎实。这样项目才会从“功能很多的 Demo”，进一步变成“结论可信、设计可解释、能够持续迭代的工业品导购 Agent”。
